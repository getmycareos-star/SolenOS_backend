# Evidence-grounded intelligence capability matrix

**Scope:** SolenOS backend and frontend `main` only. No pull request branch is part of this work.

**Status rule:** A code path or test file alone does not qualify a capability as complete. "Implemented, verification pending" means the implementation is present but the exact current `main` commit has not yet produced a completed passing workflow. "Partial" means a material part of the contract is not established end-to-end. This matrix must be updated as evidence changes; it is not a claim that all rows are complete.

## Current critical implementation slice

- A shared bounded provenance-closure loader follows explicit parent links, normalized original-source references, and persisted reviewed relationship edges without using text similarity as proof of common origin. It is person-scoped, has node/depth/relationship caps, and reports truncated retrieval as unknown rather than absent: `backend/app/services/evidence_lineage.py`.
- Exact matching stored source-text SHA-256 fingerprints now surface as `exact_content_duplicate_candidate` groups in authenticated uncertainty analysis. This does not assert common origin; it withholds the numeric independent-evidence count and requires source-independence review until resolved. Tests cover helper and API behavior.
- The shared loader is wired into uncertainty analysis, LCR context retrieval, appointment preparation briefs, and handoff drafts. The LCR projection also seeds lineage from evidence IDs referenced by bounded source records, not only the most recent evidence list.
- Regression coverage includes multi-hop lineage through an unselected ancestor, person-boundary isolation, the authenticated uncertainty API's independent-evidence count, and handoff shared-source projection: `backend/tests/test_evidence_lineage.py`, `backend/tests/test_uncertainty.py`, `backend/tests/test_handoff_drafts.py`, and `backend/tests/test_lcr_context_schema_cache.py`.
- These changes are committed directly to `main`. The exact current-main test and PostgreSQL migration runs must finish successfully before this slice is called verified; passing code-level tests does not establish all 18 capability groups are complete.
- Handoff summary attachment now validates each submitted source ID against a bounded allowlist of persisted care-record tables and the authenticated person's scope, rejects unknown/cross-person and ambiguous cross-table IDs, and stores the matching table names. This is existence/scope validation only: the snapshot explicitly records `semantic_grounding_status: not_automatically_verified`; caregiver review remains a client-declared attestation. Regression coverage was added in `backend/tests/test_privacy_delivery.py`.
- Appointment preparation includes person-scoped freshness assessments and policy version/rationale where available. Freshness schema failures must be disclosed as unavailable rather than silently treated as no assessments. Exact-current-main tests remain pending.

## Required release gates

1. **Shared-source corroboration:** exact duplicate text is only a duplicate candidate; explicit parent/source references and reviewed relationships define lineage. Similar wording is never proof of common origin or independence.
2. **Conflict lifecycle:** resolution and partial resolution require rationale and same-person evidence; each transition is appended to immutable history. Reopening must preserve previous resolution events.
3. **Temporal state:** event, observation, report, recording, ingestion and review times remain distinct. Historical reconstruction must use persisted versions, not current rows relabelled as history.
4. **Freshness/completeness:** a freshness or completeness result must cite its task/domain policy and assessment history; absent/unavailable is not a negative finding.
5. **Decision/outcome traceability:** decisions, completed actions, and observed/reported outcomes are distinct entities with explicit provenance.
6. **Grounded generation:** Companion, summary, appointment and handoff outputs must only assert what authorized retrieved records support; otherwise they disclose uncertainty or fail closed.
7. **Real verification:** current SHA, successful backend tests, PostgreSQL migration, container build, frontend validation/build and deployment evidence must be captured separately. Unit tests alone do not prove production end-to-end behavior.

## Direct-main Companion claim-grounding increment — 2026-11-24

**Status: Implemented in source; exact-current-main test and live-model verification pending. This does not close groups D, H, I, or P.**

- Companion response validation now constructs claim provenance before accepting a generated answer and rejects unmatched material care claims with a fail-closed response.
- Claim source candidates are retained only when their typed record IDs resolve to persisted rows scoped to the authenticated person's care record. Unknown, unresolved, and cross-person IDs are excluded.
- Context parsing maps shared LCR source types and LCR event/evidence prefixes to the source types used by the person-scoped enrichment path; reporter, epistemic status, source attribution, event time, and recording time are retained where supplied.
- Exact source matching now refuses to drop explicit attribution, negation, or uncertainty qualifiers. Short exact quotations are accepted only with explicit attribution framing and are recorded separately from whole-statement exact matches.
- Companion instructions now require exact wording and preserved attribution/time/negation/uncertainty for material care facts; unsupported paraphrases must not be presented as established facts.
- Regression coverage was added for unsupported paraphrases, attribution preservation, attributed exact quotes, source-type mapping, unresolved/cross-person source IDs, and fail-closed Companion responses.

## Direct-main historical projection increment — 2026-11-24

**Status: Implemented, verification pending; overall historical LCR coverage remains partial.**

- The bounded as-of projection now includes append-only evidence-review and claim-assessment events in addition to CareStateRevision snapshots.
- Both streams are filtered by the requested historical instant and joined to same-person persisted evidence or care assertions.
